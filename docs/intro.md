# netwatch 介绍

> 看什么程序在偷偷上传、传给谁、传了多少。

netwatch 是一个跑在本机的**进程级上传监控仪表盘**:一个 root 采集进程常驻记录"哪个进程在向哪个远端传数据、传了多少",一个普通权限的展示进程把这些数据呈现在 Web 仪表盘上,并对可疑的上传行为自动告警。

它只关心**行为元数据**——谁、何时、何地、多少。不看内容(不做 MITM 解密)、不拦流量(不做防火墙),定位是"让偷偷上传看得见",而不是"替你管住"。

## 一、它解决什么问题

现代桌面软件几乎都在后台上传点什么:云盘同步、相册备份、AI 客户端把文件发给服务端、浏览器扩展回传遥测……大多静默进行。系统自带工具只给得出"总流量"或"某进程用了网",回答不了最关键的一问:**传给谁**。

netwatch 把流量归因到「进程 × 目的地」两级,用域名、归属地、服务分类把远端翻译成人话,再用三条行为规则盯住异常。"备份工具是不是在把家目录往云端推""这个陌生进程为什么每分钟都往外发数据"——打开仪表盘就能看到答案。

它回答四个问题:

| 问题 | 从哪里看 |
| --- | --- |
| **现在谁在传?** | 实时视图:每个进程 → 每个远端的上传速率,秒级推送 |
| **它传给谁?** | 目的地富化:IP → 域名 → 归属地/ASN/分类徽标,一眼判断"该不该传" |
| **它传了多少?** | 历史视图:分钟粒度落库,1h/24h/7d 按进程/目的地双维度排行 |
| **什么在偷偷传?** | 告警:首次出现的目的地、超阈值的大流量、归因不到进程的持续外传 |

## 二、核心特性

- **进程级归因**:流量归到具体进程,按「进程 → 目的地」两级展示;归因失败的流量不丢弃,单独以 UNKNOWN 呈现并纳入告警
- **目的地富化**:反向 DNS(本机 DNS 查询,正/负结果缓存 6 小时)+ GeoLite2 本地库(归属地/ASN,规划接入)+ 静态分类规则表(AI 服务 / 网盘 / 对象存储徽标)
- **环回代理适配**:本机走 clash/mihomo 类环回代理时,应用看到的目的地是 127.0.0.1,真实远端藏在代理进程的连接里——富化层自动识别代理进程,用字节相关启发式把「应用 → 代理」与「代理 → 真实远端」两跳关联起来,告警归因不被代理污染
- **四条告警规则**:`new-destination`(向新公网 IP 首传)、`volume-threshold`(单进程上传量超阈值)、`unknown-process`(归因失败的外传)、`beacon`(心跳式定时小包外联);`进程 × 目的 IP` 白名单静默;notify-send 桌面通知 + webhook
- **历史回看**:分钟粒度聚合落 SQLite(明细保留 90 天),查询 CLI 与 Web 双入口
- **权限分离**:采集端(root)只写库、不开任何网络端口;展示端普通用户只读库;SQLite(WAL)是两个进程唯一的耦合点
- **Web 仪表盘**:深色主题,实时/历史/告警三视图,URL 即状态可直达;展示能力由 `capabilities` 声明驱动,平台降级不改前端代码

## 三、工作原理

### 总体架构:两个进程,一个库

```
┌─────────────── 采集进程(root)────────────────┐
│ ss 轮询 ─→ 行解析 ─→ TrafficEvent 类型化事件流  │
│                    │                           │
│            富化器(域名/分类/代理两跳)          │
│                    ▼                           │
│     聚合器(分钟桶)──定期──→ SQLite 落库        │
│     规则引擎(订阅事件流)──→ 桌面/webhook 告警  │
└─────────────────────────┬─────────────────────┘
                          ▼
                  SQLite(WAL,唯一耦合点)
                          ▲
┌─────────────────────────┴─────────────────────┐
│ 展示进程(普通用户):Hono API + SSE + React    │
└───────────────────────────────────────────────┘
```

实时数据不靠采集端开端口:采集进程每秒把活跃流快照整行覆盖写进库里的 `live_snapshot` 表,展示进程轮询该行、经 SSE 推给浏览器。root 进程零网络暴露;采集崩了不影响看历史,展示重启不丢数据。

规则配置(`~/.config/netwatch/rules.json`)由 Web 端写、采集端读,改完 SIGHUP 热重载,两个进程不需要互相发现。

### 采集:流量怎么归到进程

Linux 首发路径是 **ss 轮询**:定期执行 `ss -tinp state established`,每条 TCP 连接自带远端地址、进程归属(`users:(("name",pid=N))`,root 下全量可见)和每连接累计字节数,相邻两拍做差即增量。零抓包、零 pcap 依赖。

选型依据是 Phase 0 的真实采样:原方案 nethogs 的 trace 模式输出的是每进程聚合,**没有远端地址列**,撑不起"传给谁";它因此降级为交叉验证/无目的地降级源,解析器已按 0.8.7 真实输出校准。后续进阶路线是 eBPF kprobe 精确统计(规划中)。

### 富化:"传给谁"翻译成人话

对活跃远端做反向 DNS 得到域名,GeoLite2 本地库补归属地/ASN,静态规则表给 AI/网盘/对象存储打分类徽标("谁在往 AI 服务传文件"一眼可见)。GeoIP 全部走本地库文件——本工具监控别人联网,自己不偷偷联网。

### 规则引擎:什么算"偷偷传"

| 规则 | 触发条件(默认,可配) |
| --- | --- |
| `new-destination` | 已知进程首次向新公网 IP 上传(info;同时 > 10MB/min 升 warn) |
| `volume-threshold` | 单进程上传 100MB/10min 或 500MB/h |
| `unknown-process` | 归因不到进程的持续外传:连续 3 个采样窗口且 > 1MB/min |
| `beacon` | 心跳式外联:同进程对同一公网目的地,10min 窗口内反复小包上传、间隔规律且持续 ≥ 5min |

白名单按 `进程 × 目的 IP` 命中即静默(支持 `*` 进程级);已确认的代理中转进程豁免 `new-destination`(新目的地告警应归因到背后的应用,而不是代理本身)。告警入库供仪表盘展示,同时走桌面通知 + webhook。

## 四、数据与隐私

- 只记录连接元数据(IP、端口、域名、字节数、时间),**不接触任何传输内容**
- GeoIP/ASN 全部使用本地库文件,不做在线查询;域名走本机 DNS 的反向解析
- 所有数据存本机单个 SQLite 文件:`~/.local/share/netwatch/netwatch.db`(WAL);明细保留 90 天,采集端每小时自动清理
- 规则配置:`~/.config/netwatch/rules.json`

## 五、能力边界与已知局限

**明确不做**:内容审计(HTTPS 内容不可见,也不应做 MITM)、拦截/防火墙(那是 opensnitch 的领域)、跨主机监控(只看本机)。

**ss 轮询的已知局限**:两次轮询之间建立又关闭的短连接会漏;UDP 无字节计数。环回代理两跳关联是字节相关启发式(±25% 字节 / ±5s 时窗),多条应用流经同一代理且字节数相近时可能错配;关联只影响展示与告警标注,不改变底层归因事实。

## 六、平台支持

| 平台 | 采集方式 | 状态 |
| --- | --- | --- |
| **Linux** | ss 轮询(主路径)+ nethogs 交叉验证/降级,eBPF 为后续进阶 | 首发 |
| macOS | `nettop -P -L`(系统自带,Phase 7) | 计划 |
| Windows | ETW;降级为连接轮询(无字节数,Phase 8) | 计划 |

平台差异全部封在采集适配层(单一 `TrafficSource` 契约),上层只消费 `TrafficEvent`;降级能力由 `capabilities` 声明,仪表盘据此自动隐藏速率相关组件。

## 八、快速体验

```bash
npm install

# 无 root 体验全链路(mock 数据源,Ctrl+C 退出)
npm run collector:mock

# 构建并启动 Web 仪表盘,浏览器打开 http://127.0.0.1:8787
npm run web:build && npm run web

# 查询落库数据(采集端跑过并跨过整分钟后)
npm run query -- top 1h                   # 按进程
npm run query -- top 24h --by=destination # 按目的地

# 真实采集(Linux 主路径 ss 轮询,需要 root)
sudo npm run collector
```

常驻部署(systemd 双 unit:采集 root + 展示普通用户)与规则配置说明见 [README](../README.md)。

## 九、与同类工具的对比

| 工具 | 粒度 | 回答"传给谁" | 历史回看 | 异常告警 |
| --- | --- | --- | --- | --- |
| **netwatch** | 进程 × 目的地 | ✅ 域名/归属地/分类 | ✅ 分钟粒度 90 天 | ✅ 四条规则 + 白名单 |
| nethogs | 进程聚合 | ❌(trace 无远端列) | ❌ | ❌ |
| iftop / ss | 单条连接 | 有远端地址 | ❌ | ❌ |
| opensnitch | 进程 × 目的地 | ✅ | ❌ | 定位不同:交互式拦截防火墙 |

opensnitch 能拦,但要逐条放行、常驻开销在拦截路径上;netwatch 零拦截、只观测,适合"我想先知道发生了什么"的场景。nethogs 在本项目里没有缺席——它被收编为采集层的交叉验证/降级源。
